# I built a Go networking library with Claude: fib, almost every line written by Claude

English | [简体中文](introducing-fib.zh-CN.md)

Repository: <https://github.com/lesismal/fib>

I recently finished a new Go networking library, fib, working together with Claude. The ideas and
the direction are mine; almost all of the code was generated by Claude. It supports TCP/UDP, TLS,
HTTP/1.x, HTTP/2, HTTP/3 (QUIC) and WebSocket, and its HTTP handlers take the standard
`*http.Request` and `http.ResponseWriter`.

The short version: in benchmarks that run automatically on GitHub Actions, fib gets several
times the standard library's throughput in some scenarios, on much less memory. Against libraries
known for speed, such as fasthttp, it's faster too. Against C, C++ and Rust servers, it's close,
and ahead in some cases. The repositories those Actions live in contain the
complete benchmark code, so every number can be traced back and reproduced.

Of course, different hardware, test parameters and framework settings can give different results.
You're very welcome to run the benchmarks on your own machines.

## The numbers first

All of these come from the Docker benchmark workflows in the `lesismal/go-*-benchmark`
repositories on GitHub Actions. The runner has 4 vCPUs, 2 for the server and 2 for the client,
with 10,000 connections and a 1 KiB payload. Each is a single run on a shared runner, so treat a
few percent either way as a tie. The links have the full tables, including CPU efficiency and
latency percentiles.

The headline gains:

- HTTP/1.1: echo is 2.3× net/http; pipelining is 6.9× net/http and 1.65× fasthttp, on a tenth of
  net/http's memory
- HTTP/2: echo is 3.7× net/http; multiplexed it's 13× net/http and 2.6× Rust's h2
- HTTP/3: 3.4–5.4× quic-go's throughput, and past 90% of Cloudflare's quiche
- TLS: pipelining is 2.9× crypto/tls over `net`, on about a third of the memory
- WebSocket: the highest echo throughput of the 17 servers tested, on 32 MB

The goroutine pool under fib, [`taskpool`](https://github.com/lesismal/fib/tree/main/taskpool),
can also be used on its own. CI compares it with nbio, ants, gopool and fnet on Linux, macOS and
Windows on every push, and [it leads clearly](https://github.com/lesismal/fib/actions/runs/37020403709)
when tasks are submitted the way an event loop submits them.

None of this comes from a single trick. It comes from an architecture that works differently from
the standard library, and to explain it I have to start with threads.

## Threads are expensive

The classic C/C++ server is one process with a handful of threads. Threads cost a lot: each has a
stack, switching between them goes through the kernel, and a few hundred of them is already
heavy. With so few threads, blocking is expensive too. If one thread waits on a slow query, every
request it owns waits with it. So C/C++ network libraries mostly took the same road: epoll or
kqueue for events, non-blocking sockets, business logic split into callbacks, and a thread pool
for the slow parts. It's fast, but the code ends up cut into pieces, you keep the state around by
hand, and it's tiring to write and to read.

C/C++ and many other languages have coroutines now: C++20 coroutines, various libraries, Rust's
async/await. But most of the time you still manage the coroutine's lifetime and scheduling
yourself. Who resumes it, which thread it runs on, who owns its frame, whether a reference is
still valid across a suspension point. Compared with Erlang processes or Go goroutines, these are
noticeably harder to understand and to use.

## Goroutines, and where they stop helping

Go is much nicer here. Goroutines are far lighter than processes or threads, and a few thousand
to a few tens of thousands of them run smoothly. The standard `net` package is event-driven
underneath: the runtime's netpoller waits on epoll or kqueue and wakes the goroutine blocked in
`Read`. You get a synchronous API on top, which is a big part of why Go is so popular for servers.

The standard library gives you one way to do it, though. For a `net.Conn` you usually need at
least one goroutine sitting in `Read`. Ten thousand connections means ten thousand goroutines; a
million connections means a million goroutines, each with its own stack, plus a `bufio.Reader`
and `bufio.Writer` per connection. Most connections are idle most of the time, but that memory
stays, and the GC and the scheduler feel it. That's where most of net/http's hundreds of
megabytes in the tables above come from. Some frameworks pre-fork several processes and spread
the connections over them to take the pressure off a single runtime, but then you have
cross-process coordination, deployment and monitoring to deal with.

## What fib does: event-driven, non-blocking, and a configurable goroutine pool

For the last few years I've been working on a different approach. Like the runtime, it uses
epoll, kqueue or IOCP for events, but it doesn't park a goroutine on every connection. When a
connection becomes readable, the event loop hands it to a worker from a goroutine pool. The worker
reads, parses the protocol, calls your handler and writes the response, and then goes back to the
pool. An idle connection is just a struct. It holds no goroutine and no read or write buffer,
which is how fib stays at a few dozen megabytes in the tables above.

What makes this work is the size of the pool. A C/C++ thread pool usually has a few dozen threads.
Block in a handler and the pool runs dry, and every other connection waits, so everything has to
be async. Go is different. Even a size-limited goroutine pool can run thousands or tens of
thousands of goroutines. That's enough concurrency for a handler to keep calling downstream
services synchronously, an RPC or a SQL query, without worrying that a few slow requests will use
up the pool and leave other connections waiting.

So the event loop carries the connections, the pool carries the concurrency, and your code stays
synchronous. The number of connections and the number of goroutines are no longer tied together.

By default fib's pool allows up to `GOMAXPROCS × 1000` workers. It grows and shrinks with load and
retires idle workers, so a high ceiling costs nothing while it isn't used. Lower it if your
handlers rarely block, raise it if your downstream is slow, or bring your own pool:

```go
config := fib.DefaultConfig()
config.SetPoolSizing(20000, 0) // worker ceiling
// or config.SetTaskPool(myPool)
```

## From nbio to fib, with Claude

This isn't my first go at this design. A few years ago I wrote
[nbio](https://github.com/lesismal/nbio) by hand. It supports TLS, HTTP/1.x and WebSocket, and
quite a few people run it in production. But I only have so much time, and HTTP/2, HTTP/3 and
QUIC were too much work to take on alone.

AI models have improved fast over the last year or two, and that's what made fib possible. This
time I worked with Claude, and almost all of the code was generated by Claude. So far fib
supports:

- TCP, UDP and Unix sockets, on epoll (Linux), kqueue (macOS) and IOCP (Windows)
- TLS 1.0–1.3: crypto/tls does the handshake, and fib handles the record layer after that
- HTTP/1.x, HTTP/2 (h2 and h2c) and HTTP/3, with QUIC and QPACK written from scratch, no quic-go
- WebSocket over HTTP/1.1, HTTP/2 and HTTP/3
- async HTTP/1, HTTP/2, HTTP/3 and WebSocket clients, a chi-style router and the usual middleware

## Using it feels like the standard library

For all the talk about performance and architecture, using fib is simple. HTTP handlers take the
standard `*http.Request` and `http.ResponseWriter`, so existing `net/http` handlers,
`http.ServeMux`, `http.FileServer`, and even chi or gin engines run on fib as they are:

```go
mux := http.NewServeMux()
mux.HandleFunc("GET /hello/{name}", func(w http.ResponseWriter, r *http.Request) {
	fmt.Fprintf(w, "hello %s over %s\n", r.PathValue("name"), r.Proto)
})

config := fib.DefaultConfig()
config.Addr = "127.0.0.1:8080"
engine, err := fib.Bind(config, fibhttp.NewHandler(fibhttp.HandlerFunc(
	func(c *fibhttp.Context, r *http.Request) { mux.ServeHTTP(c, r) },
)))
if err != nil {
	panic(err)
}
engine.Run()
```

That one port serves HTTP/1.x and h2c. Put TLS in front and HTTP/2 is negotiated over ALPN. Bind
a UDP engine and it's HTTP/3. The handler doesn't change.

## Wrapping up

Since the code is mostly Claude's, testing matters all the more. fib has a lot of tests and CI
behind it: HTTP/1 conformance against net/http and curl, h2spec, HTTP/3 interop with quic-go,
the Autobahn WebSocket suite, and fuzzers. Some of my own services already run on it, and I
haven't run into problems so far.
