fib architecture

fib (Fast In Balance) is edge-triggered event loops with a pool of goroutines: the loops only wait for events and schedule the connections those make runnable onto logical workers, and every round of a connection, its reads, callbacks and writes, runs on a worker. This page describes the Go implementation as a whole, from the source at main (8a388d4). The step-by-step flow of each protocol is in Protocol flows.

event loop (root / poller) ‹Name›-workers, the engine pool fib-tls-handshake pool ‹Name›-streams pool timer goroutine the application's own goroutine

Three invariants

The whole concurrency model is reasoned about from these three rules. The rest of the design follows from them.

Descriptors belong to the event loop

Only a loop calls epoll_ctl, accepts, and finally closes a descriptor. A worker that wants reads paused, a connection closed or a descriptor released says so through the command queue and an eventfd, and a loop that is already awake needs no wake-up.

Order belongs to the connection

The unit of scheduling is the connection, not the event. The loop folds readiness into the connection's pendingEvents and does not submit it again while scheduled is set. A connection has at most one worker at a time, so OnData never runs twice at once or out of order, and OnClose always follows the OnData before it.

Connections are bound to no thread

Each round is taken by whichever worker is idle, and the next round may be another goroutine's. What is balanced is the work waiting to run, not the number of connections.

The parts

An Engine owns the listeners, the event loop, its command queue and the worker pool. With IOPollers, the default, it also owns pollers: each is an Engine without listeners, with a loop, command queue and descriptor table of its own, sharing its parent's settings, handler, worker pool and server-wide budget.

  • A worker count is a ceiling, not a population. An adaptive pool grows when a task finds every worker busy, and at intervals retires half of the workers that sat idle throughout. A high ceiling costs nothing; a low one throttles bursts.
  • A worker makes its connection's read and write system calls itself and spends much of a round in the kernel rather than on a P, so the pool is oversubscribed relative to the cores. GOMAXPROCS is best left at the runtime's default, the cores.
  • The three pools are separate. An engine worker may wait on the stream pool's or the handshake pool's queue, never the reverse, so workers cannot all end up stuck in a submission.

Handler layers

Protocols stack by wrapping a fib.Handler. Input climbs the OnData chain; output goes through Connection.Send, and through the connection's Layer first when it has one. The handler on top always sees an ordinary connection.

  • A fib.Handler has four callbacks: OnOpen, OnData, OnPriorityData and OnClose. OnOpen runs on the event loop, the others on workers.
  • One http.Handler can serve HTTP/1 and HTTP/2 (a TCP engine) and HTTP/3 (a UDP engine), answering through the same Context.
  • WebSocket attaches in two ways: websocket.ServerHandler as a fib.Handler itself, or Upgrade called from an HTTP handler, which switches the whole connection on HTTP/1.1 and one stream on HTTP/2 and HTTP/3.
  • The HTTP middleware (compress, cors, csrf, etag, limiter, logger, pprof, recover, requestid, responsetime) wraps an http.Handler and knows nothing of the transport.

Reading and scheduling

From a kernel event to the application's callback and back to a connection that can be scheduled again. A loop submits one batch of connections per round, rather than one lock-and-wake cycle per connection.

  • Coalescing. Readiness is level information to a connection, so repeated notifications are or-ed together and a hot connection cannot grow an unbounded event queue. A notification that is only EPOLLOUT with nothing queued is dropped, which keeps every new connection from being scheduled a second time.
  • Giving up the P. After submitting, the loop calls Gosched so that the workers it just woke run on its P straight away. With 4 Ps serving HTTP/2 echoes over 10k connections that was worth 10% to 25%.
  • A loop holds no P while it waits. With IOPollers a loop parks in the Go runtime's network poller instead of blocking in the epoll_wait system call.
  • Read buffers are borrowed per round. The 16KB read buffer comes from bufferpool for the round and goes back at its end, so an idle connection holds none. A short read says the socket is empty, and no further read is made only to get EAGAIN.
  • UDP is the exception. The loop reads a shared UDP socket itself, in batches, and queues each datagram on its peer's connection; the worker's round only hands the queue to the handler.

Writes and backpressure

What can be written at once is written at once; only the rest is queued. Queued bytes have two bounds, a watermark per connection and a budget for the whole engine, and crossing either pauses reads, leaving TCP flow control to slow the peer.

  • Write interest is permanent. EPOLLOUT is armed from registration on, so queueing needs no registration change; only a watermark crossing costs an epoll_ctl.
  • Cork. A round's replies accumulate in one contiguous buffer and reach the socket in one write when it ends. A handler streaming a response calls Flush to send its first part early, and an application may Cork for itself.
  • Hysteresis. Reads pause at the high watermark (64KB by default) and resume at a quarter of it, so that replies do not cross the line back and forth; the budget (1GiB by default) likewise resumes at a quarter. At high connection counts the budget is the bound that holds.
  • A connection paused by the budget may have nothing of its own left to flush, and so no event of its own to re-evaluate it. The loop keeps such connections in budgetPaused and resumes them when the budget recovers, and a connection on another poller that drains the budget wakes the loops holding some.
  • Read-side backpressure. HoldReads lets an application stop reading while it works through what it has, as a streamed request body does; releasing it redelivers what the socket already held.
  • Stats() reports how often each kind of pause happened, how many have been lifted and the total queued now. SendFile uses sendfile and is not charged to the budget.

Close and reclaim

Every close takes the same path through the loop. The connection stops at once, but OnClose and the descriptor's release are queued with its rounds, as an event is.

  • While a round is still running on a worker, the descriptor it reads and writes is not closed, and so cannot be handed to another connection under it.
  • Descriptor reuse is guarded by a generation: a token's low half is the descriptor and its high half a generation, so an event left over from a descriptor's previous owner resolves to nothing.
  • Closing your own connection in OnData and then waiting for what OnClose reports deadlocks: that report waits for this round to return.
  • When an engine closes it stops its loops and pollers, waits for the rounds in flight, and then runs the last rounds still owed, so no closed connection loses its OnClose.

Load balance

Connections spread evenly are not work spread evenly: a few hot connections or heavy tasks can land on one thread. fib deals with that at four levels.

LevelWhat it doesCost and trade-off
WorkersEach round of a connection goes to an idle worker, with no affinity; the adaptive pool queues by P and takes batchesA handler that blocks holds up its own connection only, and the pool grows to absorb it
PollersAccepted connections go to fd % pollerCount; a poller only waits, about 0.2µs a request against 4.5µs on the workersMore pollers compete with the workers for Ps; one per 4 CPUs is the default
AcceptThe root loop accepts and hands on by default; on Linux ReusePort has every poller listen and accept for itselfReusePort lifts the one loop's accept ceiling, but a connection stays on the poller the kernel's hash chose, however busy
MultiplexingHTTP/2 and HTTP/3 handlers run on the stream pool, so one connection's requests are served concurrentlyMaxConcurrentHandlers bounds one connection; the request over the limit runs on the reader

Buffers and memory

  • bufferpool is one package-level pool for the process. Every capacity is a power of two, which is exactly one of Go's allocator size classes, so nothing is paid for rounding, and each class keeps a reserve behind its sync.Pool that a collection does not empty.
  • Read buffers are 16KB and borrowed per round. The bytes are lent to the handler for the length of OnData; protocol parsers parse in place and copy only what is left over.
  • Send buffers are taken at twice the read buffer, aligned to a pool class, which holds a round's replies. A buffer a single large message grew goes back to the class its capacity belongs to and cannot inflate the ordinary ones.
  • The connection table is paged and indexed by descriptor, 4096 entries a page: a lookup is two bounds checks rather than a hash, and only the page directory ever grows.
  • TLS keeps no crypto/tls buffers after the handshake and opens records straight from the round's read buffer. Each UDP datagram takes a buffer from the pool, which QUIC gives back when it is done.

Platform backends

The rest of the engine is written against readiness. Each backend translates what it observes into the same event bits, so the workers, the queueing and the backpressure are the same code everywhere.
