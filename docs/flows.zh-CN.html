fib 事件循环与协程池流程图

按协议逐一画出：哪个事件循环等事件，哪个协程池跑哪段代码，数据和控制在它们之间怎么流动。依据当前 main（8a388d4）的源码，平台按 Linux epoll / macOS kqueue 描述，配置按 CPU 多于 4 个时的 fib.DefaultConfig()：IOPollers=true（4 个及以下默认关闭，由 Engine 自己的循环服务连接）、TaskPoolMode=ModeAdaptive、SharedTaskPool=true、SocketSyscalls=true。

协程池一览

服务端一共只有三类池，外加 Go 运行时定时器。事件循环本身从不执行连接的一轮，只等事件、合并事件、批量提交。

执行者来源模式 / 规模跑什么
事件循环Engine.runLoop根循环 1 个；poller 数为 NumCPU÷4 向下取整（至少 1）：7 核以内 1 个，8 核 2 个，16 核 4 个；IOPollerCount 可改epoll_wait/kevent、accept、UDP 收包分拣、命令队列（close / refresh / detach / accept）、OnOpen
‹Name›-workersacquireTaskPool（shared_taskpool.go）Adaptive（按 P 分片入队）；上限 max(GOMAXPROCS×1000, NumCPU×20)，常驻下限 MinWorkerCount，同 Name 的 Engine 共用Connection.RunTask → process()：读 socket、OnData 链（TLS 解密 → 协议解析 → HTTP/1 handler / WS 回调）、写合并、OnClose
fib-tls-handshakesidepoolAdaptive；上限 65536，队列 10000，下限 0，进程内全局共享crypto/tls.HandshakeContext 这个阻塞调用，以及与握手同到的首批明文的交付
‹Name›-streamsstreampool，Engine.HandlerPool()Adaptive；上限 = 同 Name 最宽引擎池 ×2，下限 0HTTP/2、HTTP/3 的请求 handler（含扩展 CONNECT 的升级和 WebSocket OnOpen）；HTTP/1 的 OnBody 交接、连接关闭时的取消通知
定时器time.AfterFunc运行时按需读写 deadline → commandClose；UDP 空闲扫描 → commandUDPSweep；QUIC 的 ACK / 丢包 / 空闲 / flushHold 定时发送

三个池必须互相独立：引擎 worker 向流池提交 handler、向握手池提交握手，队列满时会等待；如果共用同一个池，所有 worker 都可能卡在提交上，没人去消费队列，事件循环也会跟着停住。等待只能单向发生：引擎 worker 等流池/握手池，反过来从不发生。

另有 fib-client（sidepool，上限 4096），只给客户端的 DNS 解析和结果回调用，服务端流程不涉及。池的模式现在只有 ModeElastic、ModeAdaptive、ModeAdaptiveChan 和 ModeInline，ModeCond 已移除；Engine 不接受 ModeInline。

  • 不开 IOPollers：没有 poller，根循环自己 accept、注册、等所有连接的事件，其余相同。
  • ReusePort（仅 Linux）：每个 poller 在同一地址上 listen 自己的 socket，自己 accept；根 socket 只 bind 不 listen。UDP 同理，每个 poller 读自己的 UDP socket。
  • OnOpen 在事件循环上执行（admit / udpPeer），所以 OnOpen 里不能阻塞；TLS 正是在这里把握手交给握手池。
  • worker 在轮外发送（Send 在非 corked 状态）会直接写 socket；写不完才排队、靠常驻的 EPOLLOUT 边沿续写。
  • Linux 上连接的读写是不经调度器的原始系统调用（socket 非阻塞，不会等待）；SocketSyscalls 默认开启时用 recvfrom / sendto / sendmsg，绕开 VFS 层的权限钩子。
  • 关闭由循环执行 closeConnection：立即停止收发、释放预算，但 OnClose 和 fd 释放被折叠进该连接的下一轮，保证 OnClose 在之前的 OnData 之后。

一轮 round：worker 上的 process()

所有 TCP 协议的回调都在这里被调用。每一轮的回复被 cork 住，在轮末合并成一次 write / writev。

  • 一条连接同一时刻最多只有一个 worker 在跑它（scheduled 标志），循环在这期间收到的事件只并入 pendingEvents，由这一轮在结尾处接着处理。

TLS（fibtls.NewServer 包裹任意 fib.Handler）

握手是 crypto/tls 的阻塞调用，放进独立的握手池；它要读的密文仍由引擎 worker 读 socket 后喂进来。握手完成后，AES-GCM / AES-CBC 套件改由 fib 自己加解密，在 worker 上直接从本轮的读缓冲解密。

HTTP/1.x（明文）

一条连接的一个请求，从第一个字节到响应，都在同一个 worker 的同一轮里完成，handler 也在这个 worker 上执行。流池只处理 handler 返回之后才需要交付的事情。
