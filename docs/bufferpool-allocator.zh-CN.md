# bufferpool：自定义分配器与严格 Get/Put 配对

[English](bufferpool-allocator.md)

[`bufferpool`](../bufferpool) 保持直接返回和传递 `[]byte` 的接口，用户可以通过 `SetAllocator` 换上自己的分配器（第 1 节）。本文其余部分是一份分析，没有对应的实现。问题是：换上手动管理内存的分配器（例如用 cgo 调 jemalloc）时，能否做到：

- **Put 只接收本池取出的缓冲区**，外来的一律不收；
- **Get 与 Put 严格一对一**，不能有泄漏。

分析基于 2026-11-17 的 `b070cc6`。下文的数字都是在 Apple Silicon、14 核、Go 1.27.3 上测得的。

## 结论

1. **可插拔分配器本身没有性能代价。** `Get`/`Put` 开头判断 `atomic.Pointer` 是否为 nil，为 nil 就走内置池，实测和加入前一样快。这部分已经实现。
2. **“只收自己的缓冲区”只能由分配器判断。** 仅凭一个 `[]byte`，fib 无从知道它的来源。
3. **fib 现在做不到严格一对一。** 现有约定本来就是“任何缓冲区都可以 Put，不 Put 的交给 GC”，代码里有大量依赖这条约定的路径。要接手动管理内存的分配器，必须先改约定，再把这些路径全部修掉。
4. **用 cgo 调 jemalloc，每对 Get+Put 比现有池慢好几倍。** 它能省下的 GC 开销，现有设计大部分已经省下了。
5. **不加按 fd 分片的 `GetBy`/`PutBy`。** sync.Pool 本来就按 P 分片、没有全局锁，按 fd 再分一层没有收益；buffer 换了 fd 还回时，会慢 20 到 170 倍。

## 1. 分配器接口：nil 回退（已实现）

```go
type Allocator interface {
    Get(size int) []byte
    Put(buf []byte)
}

// SetAllocator 应在任何组件取用缓冲区之前调用一次；nil 恢复内置池。
func SetAllocator(a Allocator)
```

实现在 [allocator.go](../bufferpool/allocator.go)：

- **默认路径**：`Get` 和 `Put` 开头各加载一次 `atomic.Pointer`，为 nil 时走内置池，其余代码不动。
- **Get**：`size <= 0` 仍然直接返回 nil，不经过分配器；其余尺寸全部交给分配器，包括超过 `MaxSize` 的。分配器返回的切片 len 必须等于 size，cap 至少为 size。
- **Put**：cap 为 0 的缓冲区直接忽略；其余全部交给分配器，由它决定如何处理不是自己发出的缓冲区（第 2、3 节）。
- **Grow、Append、Join**：通过 `Get`/`Put` 走同一个分配器；容量够用时的快路径不经过分配器。
- **Align、MinSize、MaxSize**：仍描述内置池，fib 用它们决定申请多大的缓冲区。`SetRetainedBytes`、`RetainedBytes` 只作用于内置池。
- **切换时机**：分配器应在启动前设置。换掉时还在外面的缓冲区，Put 时会交给当时的分配器。

设计时实测的 Get+Put 一对耗时：

| 方案 | 单线程 | 14 核并行 |
| --- | --- | --- |
| 原实现 | 8.15 ns | 1.02 ns |
| 包内 nil 判断，普通全局变量 | 7.74 ns | 1.12 ns |
| 包内 nil 判断，`atomic.Pointer` | 8.16 ns | 1.11 ns |
| 包级接口变量，默认实例也走接口 | 约 +1.5 ns | 约 +0.2 ns |

前三者的差距在噪声以内。最后一种多了一次间接调用，`Get` 的主体也不能再内联到调用方。因此选了 `atomic.Pointer`：速度一样，而且在 `-race` 下不会报竞争。

实现后，包内基准与加入前对比（各 8 次的平均值）：

| 基准 | 加入前 | 加入后 |
| --- | --- | --- |
| `GetPut/64B` | 7.54 ns | 7.62 ns |
| `GetPut/1500B` | 7.64 ns | 7.64 ns |
| `GetPut/16384B` | 7.58 ns | 7.70 ns |
| `GetPutParallel` | 1.03 ns | 0.86 ns |
| `JoinParts/pooled` | 24.02 ns | 24.07 ns |

## 2. Put 只接收本池的缓冲区

判断只能在分配器内部做：

- **地址登记表**：发出去的每个地址记进一张分片 map，Put 时先查，查不到的缓冲区忽略，交给 GC。能挡住外来缓冲区和重复 Put。每次 Put 多一次查表，粗估 20–50 ns，未实测。
- **地址区间**：分配器预留一段连续地址自己做分级，比如 jemalloc 的专用 arena 加自定义 extent hooks，或者自己 mmap 一块内存。Put 只需比较地址是否落在区间内，是 O(1)。
- **不能用 `malloc_usable_size` 之类的函数去判断外来指针。** 对不是 jemalloc 分配的指针调用它，属于未定义行为。
- **要拒绝指向缓冲区中间的指针**（`buf[k:]` 这类截过的切片）。free 一个中间地址会直接崩溃。这次测试中没有发现 fib 这样 Put 过。

## 3. 严格一对一：fib 当前的差距

### 测法

在 fib 的一个临时副本里给 `bufferpool` 加了配对跟踪，用环境变量开启：

- Get 时按缓冲区的基地址登记，记下调用栈；
- Put 时核销。登记表里没有的，按情况记为“外来缓冲区”“中间指针”或“重复 Put”；
- 每次新分配都挂一个 `runtime.AddCleanup`。缓冲区被 GC 回收时如果仍未 Put，记为泄漏。

然后用 `-short` 跑了全部 88 个包，全部通过。

### 结果

| 问题 | 生产代码中的位置数 | 例子 |
| --- | --- | --- |
| Get 后没有 Put，交给 GC | 48 处 | `core.(*Engine).deliverDatagram`：连接关闭时排队中的 datagram 没有还回池；`http.(*Parser).appendBuffer` |
| Put 了不是从池里取的缓冲区 | 29 处 | `http.(*h2ServerConn).sendPooledLocked`、`tls.(*layer).releaseInLocked`、`websocket.(*Parser).releaseInflated` |
| 疑似重复 Put | 2 处 | `http.(*clientRequest).releaseData`、`http3.(*clientStream).send` |
| Put 中间指针 | 0 处 | — |

泄漏是在 GC 回收时才发现的，所以只是下限。其中有一部分是测试直接丢弃连接造成的，但这些路径确实都没有配对。

那两处疑似重复 Put，同一个位置也报了外来缓冲区。推断是跟踪器的误报：GC 回收之后、清理回调运行之前，同一个地址已被新的 Go 分配用上，于是被当成重复 Put。这一点没有证实。

### 典型模式

`http` 包 `fastFramedRequest`（[client_codec.go](../http/client_codec.go)）：

1. 先 `bufferpool.Get(size)`，再用普通的 `append` 往里写；
2. `size` 没有把 URL 路径的长度算进去，路径一长，`append` 就在 Go 堆上重新分配；
3. 结果是池里取出的那块被丢给 GC，后来由 `releaseData` Put 回去的却是 Go 堆上的新内存。

在现有约定下这不是 bug。换成 jemalloc 以后，前一块是真正的内存泄漏，后一块会被 free 一个 Go 堆指针，进程崩溃。

### 要做到严格配对需要什么

1. **改约定**：`Put` 只接收本池取出、且未被替换过底层数组的缓冲区；每次 Get 在所有路径上都恰好 Put 一次，包括关闭、出错和 panic 路径。
2. **修复上面这些位置**：所有“先 Get 再 append”的写法改用 `bufferpool.Append`/`Grow`；队列和缓存在连接关闭时要释放；不是来自池的缓冲区不再 Put。全部调用点约 270 处，分布在 55 个文件里，这是一轮完整的审计。
3. **把跟踪模式做成 fib 的调试功能**（例如用 build tag 开启），在 CI 里常驻，防止以后再退化。

还有一类风险 fib 内部消除不了：交给用户回调的缓冲区（OnData 的数据、WebSocket 消息）如果被用户留到回调之外再用，现在只是读到被复用的数据；换成手动管理的内存后，就是访问已释放的内存，可能段错误或内存损坏。

## 4. cgo 与 jemalloc 的开销

本机没有装 jemalloc，用系统 malloc 代替。主要开销来自 cgo 调用本身，jemalloc 自身也是十几纳秒量级。

| | 单线程 | 14 核并行 |
| --- | --- | --- |
| cgo 空调用 | 13.8 ns | — |
| cgo malloc+free 一对 | 49.6 ns | 9.5 ns |
| bufferpool Get+Put 一对 | 约 7.5 ns | 约 1 ns |

jemalloc 能省下的只是 Go 堆上的 GC 压力，而现有设计已经省下了大部分：

- 池里存的是 `*byte`，Put 时不需要把切片头装箱，Get/Put 都是 0 次分配；
- 缓冲区不含指针，GC 不扫描它们；
- GC 清空 `sync.Pool` 之后要重新分配工作集，这部分开销由每个分级后面的 reserve 兜住。

如果目标是降低 GC 开销，更划算的做法依次是：

1. 先调 `SetRetainedBytes` 和 `GOMEMLIMIT`；
2. 在 Go 里直接 mmap 一块不在 Go 堆上的内存，自己做分级管理，不需要 cgo，前面仍然用现在的池；
3. 真要接 jemalloc，前面也要挡一层 Go 侧的每 P 缓存，用来分摊 cgo 调用的开销。

## 5. 按 fd 分片：`GetBy`/`PutBy`

设想是加两个带 key 的方法：

```go
func GetBy(key uintptr, size int) []byte
func PutBy(key uintptr, buf []byte)
```

每个连接传入自己的 fd，自定义分配器自带多组 sync.Pool，按 `fd % N` 选一组，以此避开“全局只有一个 sync.Pool”的锁争用。

### 前提不成立

sync.Pool 没有全局锁，它本身就是按 P（也就是按 CPU）分片的：

- 每个 P 有一个私有槽，外加一个无锁的共享队列；
- Get/Put 的快路径只是把当前 goroutine 固定在 P 上，再读写本地槽，不加锁，基本也没有 CAS；
- 只有某个 Pool 第一次在某个 P 上使用时，才会拿一次全局锁。

按 CPU 分片已经是最合适的切法。再按 fd 分一层，同一个 P 要服务很多 fd，会轮流碰到很多个 Pool，缓存占用变大，命中率反而下降。

bufferpool 里其余共享的东西也不会争用：`gcEpoch` 这类计数器基本只读；reserve 的锁只在 GC 后的那一轮补充中才拿。

### 实测

在临时副本里加了 `GetBy`/`PutBy`（未装分配器时直接转给 `Get`/`Put`），并写了按 fd 分片的分配器：每个分片里每个尺寸档一个 sync.Pool。负载是 14 核并行，1 万个 fd 随机轮换，尺寸在 200B 到 16KB 之间混合，每格取 5 次的平均值：

| 方案 | 每次只拿 1 个 | 同时拿着 64 个 | 拿着 64 个，用另一个 fd 还 |
| --- | --- | --- | --- |
| fib `Get`/`Put`（现状） | 1.40 ns | 1.49 ns | 1.49 ns |
| fib `GetBy`/`PutBy`，未装分配器 | 1.41 ns | 1.51 ns | 1.52 ns |
| 不分片，每档一个 sync.Pool | 1.30 ns | 1.45 ns | 1.51 ns |
| 按 fd 分 16 片 | 2.68 ns | 3.00 ns | 28.7 ns |
| 按 fd 分 256 片 | 1.68 ns | 2.71 ns | 256.9 ns，每次都要新分配 |

单线程下，未装分配器的 `GetBy`/`PutBy` 是 9.56 ns，`Get`/`Put` 是 9.07 ns。API 本身的开销在可接受范围内，问题出在分片。

### 收益与代价

- **收益：没有。** 即使 Get 和 Put 用同一个 fd，分片也只会更慢，因为它要解决的锁争用不存在。
- **跨 fd 时严重变慢。** fib 里 buffer 经常不在取它的连接上还：读缓冲区变成回复、变成 TLS record；HTTP/2 和 HTTP/3 多路复用；广播时一个 buffer 发给多个连接。换了 fd 还，buffer 就进了别的分片；下次在原分片取时拿不到，sync.Pool 会去别的 P 的队列里找，再找不到就新分配。上表最后一列就是这种情况。
- **不常复用的 buffer 更多。** 每次 GC 会清空所有 sync.Pool，分片越多，要各自重新攒起来的就越多，空闲占用也成倍增加。这一点没有量化。
- **改动量大。** 约 270 处调用都要把 fd 传下去，`Grow`/`Append`/`Join` 也要各加带 key 的版本；而 http parser、tls、h2 这些层本来拿不到 fd。

这和之前否决的按 fd 分片分发任务（fnet 的做法，实测 fib 慢 1–3%）是同一个道理：按 CPU 切已经是最好的，按 fd 再切只会增加跨分片的开销。

如果真正的需求是按连接统计或限制内存，应该在 Connection 那一层记账，而不是拆分 bufferpool。

## 6. 长时间持有与请求风暴：储备的修复与分片

来自 [lesismal/fib#1](https://github.com/lesismal/fib/issues/1)：一个 WebSocket 服务，请求在业务队列里要等 3–8 秒，而 GC 每 200–600 毫秒一次。测量用的是 issue 作者的云服务模拟器（16 个 eventloop → 16 个 worker，每 12 秒一波 160 万请求，每 400 毫秒强制一次 GC，1 KiB buffer，预算 1 GiB），改成只用公开 API，在空闲的 Ryzen 7800X3D（16 线程）上每项跑 3 轮。

### 包内默认池的四个修复

1. **buffer 被持有跨过多次 GC 时目标会塌掉。** 到下一次 GC 还没填满的回填会把目标降到储备当时持有的数量，可它在等的 buffer 其实还在请求手里。500 个 buffer 跨过两次 GC，目标就从 500 掉到 1。现在一档在最后一次新分配或把储备取空之后，会在 `SetRetainedFor`（默认 1 分钟）内保持目标。
2. **不再有归还的档永远不释放储备**，因为释放只在归还时才会开始。现在由 GC 回调释放：一档连续两次 GC 没有归还、并且窗口已过，就把它的储备还掉。
3. **`keep` 可能抹掉刚开始的回填**：它在别的 goroutine 设好 `refill` 之后又写回 0。现在改为让计数留在负数。
4. **`trim` 用"读再写"降目标**，会丢掉并发未命中的加一，而预算还记着那一份。现在改用 CAS，并且最多只走目标当时那么多步，未命中加得和它减得一样快时也不会一直循环下去。

### 储备拆成分片

修复之后储备保住了整个工作集，每次 GC 之后的取和还都要经过它唯一的一把锁：在模拟器上波浪吞吐因此降了 11%。现在每档储备拆成多个分片，每个分片一个列表、一把锁。默认每个 GOMAXPROCS 4 个，最少 16、最多 128；`SetReserveShards(n)` 可以设成别的数量，向上取 2 的幂、最多 1024，并返回实际设置的数量。持有量和目标仍然按档只记一份，所以只要这一档还有空间，就不会有哪个分片先满；普通路径也碰不到分片：只有 GC 清空 sync.Pool 之后才会从储备取，只有随后那一批回填才会往储备还。`SetReserveShards` 会把储备里已有的 buffer 挪到新分片里，任何时候调用都可以。

### 按内存决定的预算

原来固定 32 MiB 的默认值，远小于跨 GC 持有请求的服务所需：进行中的 HTTP/2、HTTP/3 流，或者 issue 里那样的队列，都会持有几百 MB。现在默认预算是进程可用内存的 1/8，最少 32 MiB、最多 16 GiB。可用内存取机器（或 cgroup）的上限与 `GOMEMLIMIT`（设置了的话）中较小的一个；两者都读不到时预算仍是 32 MiB。预算是活跃堆：`GOGC=100` 下，填满的储备 R 在峰值时最多占 2R，所以 1/8 能把它控制在内存的四分之一以内。

- `SetRetainedPercent(p)` 把预算设为可用内存的 p%，返回实际设置的字节数；p 不在 0–100 或读不到内存时返回 error。
- `RetainedBytesLimit()` 返回当前的预算。
- `SetRetainedBytes`、`SetRetainedPercent` 和 `SetReserveShards` 每次都通过 `fib/log` 以 Info 级别打印设置的值。启动时选定的默认值以 Debug 级别打印，所以什么都不改的程序不会输出。

先做过一个所有规格都可配置的独立 `Sharded` allocator，后来放弃了：同样的算法经过 `SetAllocator` 的接口调用，每次 Get+Put 多 2–2.5ns；它另外唯一的用处——每个实例单独一份预算——没有使用场景。

先验证了 issue 作者自己的两个版本。v1 就是修复 1。v2 加了 16 个分片，但即使不在回填期间，每次 Put 也会扫一遍所有分片：在空闲机器上，普通 Get+Put 从 11.5ns 变成 26.6ns，16 线程并行从 1.39ns 变成 3.28ns。这里的分片和原来的单个列表一样，先看按档记的回填额度。

试过再给目标封顶，后来放弃了：用"两次 GC 内绕过 sync.Pool 的请求数"做上限，只要一波请求跨过更多次 GC 就会少算（小堆里一波 200 个 buffer 跨了三次 GC）。少算会导致重新分配，比目标虚高（只多占了预算的记账）更糟。

### 结果

| GOMAXPROCS=16 | 每波重新分配（第 1–5 波均值） | 波浪吞吐 | 持续 30 秒 | 堆峰值 | Get+Put 单线程 | Get+Put 16 线程 |
| --- | --- | --- | --- | --- | --- | --- |
| 修复前 | 15.4% | 2.79 M/s | 3.18 M/s，重新分配 0.21–0.29% | 559–566 MB | 11.6 ns | 1.33 ns |
| 修复后，1 分片 | 4.5% | 2.39 M/s | 3.07 M/s，0–0.02% | 454–503 MB | 11.3 ns | 1.32 ns |
| 修复后，默认（16 分片） | 2.8% | 2.74 M/s | 3.16 M/s，0% | 319–482 MB | 11.3 ns | 1.31 ns |
| 修复后，64 分片 | 2.7% | 2.78 M/s | 3.17 M/s，0% | 484–501 MB | 11.4 ns | 1.33 ns |

| GOMAXPROCS=2 | 每波重新分配 | 波浪吞吐 | 持续 30 秒 |
| --- | --- | --- | --- |
| 修复前 | 15.8% | 2.75 M/s | 3.09–3.24 M/s，0.29% |
| 修复后，1 分片 | 3.8% | 2.48 M/s | 3.05 M/s，0% |
| 修复后，默认（2 分片） | 3.4% | 2.58 M/s | 3.06 M/s，0% |
| 修复后，64 分片 | 3.2% | 2.73 M/s | 3.15 M/s，0% |

Get+Put 是 10 次的中位数。目标学到之后，一波请求经过的 GC 完全不再重新分配；剩下的都在前一两波、目标还在学习的时候。

- 修复让每波重新分配的量减少了五分之四以上，堆峰值也跟着下降：重新分配的 buffer 都是新的堆分配，GC 要追着它跑。
- 一把锁让波浪吞吐降 11–14%；16 线程下默认分片几乎全部收回。2 线程时默认只有 2 个分片，64 分片更好（2.73 对 2.58 M/s），因为 8 个 eventloop 和 2 个 worker 仍在同时归还；这种形态的程序可以调大。
- 普通 Get+Put 的开销和修复前一样，单线程和 16 线程都是。
- 结束时留住的更多（1 GiB 预算下 480–680 MB，修复前 145 MB），这正是目的：储备现在保住了队列跨 GC 持有的工作集。上限仍由 `SetRetainedBytes` 决定。

## 附：为什么不改成传递包装对象

另一个思路是参考 [valyala/bytebufferpool](https://github.com/valyala/bytebufferpool)，改成传递 `*ByteBuffer`。结论是不划算：

- **GC 方面没有收益。** bytebufferpool 要避免的是 `sync.Pool.Put([]byte)` 时切片头被装箱，fib 存 `*byte` 已经避免了。包装对象反而多一个含指针的堆对象，GC 要扫描它。
- **性能更差。** 在混合尺寸的并行负载下，按 bytebufferpool 设计重写的单池比 fib 慢 5–8 倍：共享计数器有争用，没有分级，超过 maxSize 的缓冲区会被丢弃。在 fib 的分级池外面包一层 `*Buffer`，每对 Get+Put 多约 1.4–2 ns。
- **包装对象真正的价值在于能带额外字段**：owner 指针（Put 能回到正确的分配器）、引用计数（零拷贝广播）、元数据。这些需求出现时，可以在相应路径上局部引入带 owner 的包装类型，不必改动全部调用点。
