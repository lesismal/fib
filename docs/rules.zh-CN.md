# fib 开发规则

[English](rules.md) | 简体中文

fib 的每个改动都遵守的规则，与代码如何组织和验证（[路线图](roadmap.zh-CN.md)、[开发计划](dev-plan.zh-CN.md)、[压测](loadtest.zh-CN.md)）并列。

## 1. 清理

1. **每次开发、测试和基准运行结束后都要清理自己留下的东西，释放占用的空间。** 工作完成后（一个功能、一次修复、一次
   测试或基准运行、一次复现），清除它在本机和基准测试主机上留下的东西：为它产生的构建输出（二进制、`go test -c`
   生成的测试二进制、压测构建）、源码树副本和 git worktree、它创建的容器、镜像和卷，以及不再需要的日志和临时文件。
   有意保留的缓存（Go 的构建和模块缓存、固定版本的镜像）保留，但增长后要修剪。基准测试主机的磁盘由所有会话共用：
   大规模构建或运行前先查看剩余空间（`df -h /`），离开时不要比来时更满；磁盘写满会让所有人的构建和运行停下。

## 2. 功能开发与压测

2. **功能开发任务只跑基础的 CI 测试，不做压测和基准测试。** 开发功能或修复 bug 的任务只跑 CI 所跑的内容：它涉及的
   包的测试（推送前再跑一次 `go test -race ./...`）、vet 以及 CI 跑的检查。不做压测、基准测试、A/B 对比、性能剖析、
   完整测评框架运行，也不做压力和长时间稳定性测试（大量重复次数、长时间带负载运行），本机和基准主机上都不做。基
   准主机的时间留给维护者另外单独进行的压测任务（HTTPArena 等）；功能任务占用主机既浪费机器时间，也会干扰或拖延这
   些压测。其他规则要求测量的，功能任务留给这样的压测任务，并在报告中写明应当测什么。只有用户在该任务中明确要求时，
   功能任务才跑基准测试。功能需要基准测试的（处在热路径上：引擎读写、解析器、分帧、加解密、流控、各种池），功能
   任务在[开发计划](dev-plan.zh-CN.md)中新增或保留它的行，标为未测、未优化，并在其中写明应当测什么；测量或优化它的
   压测任务负责更新这一行。

## 3. 卡死的运行不能无人察觉

3. **测试卡死只能浪费几分钟，不能浪费几个小时。** 让测试死锁的 bug 必须让运行很快、明显地失败，绝不能让它一直等下去：
   - **每个测试二进制都有时间上限。** 每次 `go test` 都显式传入与所跑内容相称的 `-timeout`（完整测试：`-timeout 20m`，与 CI 一致；
     单个慢测试：它平常耗时的几倍），绝不用 `-timeout 0`。超时后 Go 以 `panic: test timed out` 让该二进制失败，并打印
     仍在运行的测试和每个 goroutine 的栈，能看出卡住的是哪个测试、卡在哪里。
   - **超时和其他失败一样对待**：要报告，并单独重跑该测试几次（`-run <Test> -count=5 -timeout ...`），区分偶发卡死和
     改动引入的死锁。
   - **等待长时间运行的人要盯进度，而不只是等结束。** 监视程序检查日志（`go test -v` 或 `-json` 的输出）是否持续增长，
     15 分钟没有增长就报告；然后查看正在运行的进程（`ps`，对测试二进制用 `kill -QUIT <pid>` 拿到 goroutine 栈）。
     只等结束标记是不够的。
   - **测试自带截止时间。** 等待连接、channel 或条件的测试要设置读写 deadline、带超时的 `select` 或带截止时间的
     context，让 bug 使测试失败，而不是卡死。
