fib event loops and goroutine pools, protocol by protocol

For each protocol: which event loop waits for events, which pool runs which code, and how data and control move between them. Drawn from the source at main (8a388d4), for Linux epoll and macOS kqueue, under fib.DefaultConfig() on more than four CPUs: IOPollers=true (on four or fewer it is off and the engine's loop serves the connections itself), TaskPoolMode=ModeAdaptive, SharedTaskPool=true, SocketSyscalls=true.

A colour always means the same executor:

The pools

A server has three kinds of pool, plus the Go runtime's timers. An event loop never runs a connection's round: it waits for events, folds them into connections and submits those in batches.

The three pools have to be separate. An engine worker submits handlers to the stream pool and handshakes to the handshake pool, and waits when a queue is full. Were they one pool, every worker could be waiting in a submission with none left to drain the queue, and the event loop would stop behind them. Waiting only runs one way: an engine worker may wait on the other two pools, never the reverse.

There is also fib-client (sidepool, ceiling 4096), which only runs clients' DNS lookups and result callbacks. Pool modes are now ModeElastic, ModeAdaptive, ModeAdaptiveChan and ModeInline; ModeCond is gone, and an engine refuses ModeInline.

  • Without IOPollers there are no pollers: the root loop accepts, registers and waits for every connection itself. The rest is the same.
  • ReusePort (Linux only): each poller listens on a socket of its own at the engine's address and accepts for itself; the root socket is bound but does not listen. UDP likewise: each poller reads its own UDP socket.
  • OnOpen runs on the event loop (admit / udpPeer), so it must not block. That is where TLS hands the handshake to its pool.
  • A send made outside a round (Send while not corked) writes to the socket at once. Only what the socket does not take is queued, and the standing EPOLLOUT edge carries it on.
  • On Linux connections read and write with raw system calls that bypass the scheduler, since a non-blocking socket never waits. With SocketSyscalls, the default, they are recvfrom / sendto / sendmsg, which skip the VFS permission hooks.
  • The loop closes a connection in closeConnection: it stops at once and gives back its budget, but OnClose and the descriptor's release are folded into the connection's next round, so OnClose always follows the OnData before it.

One round: process() on a worker

Every TCP protocol's callbacks are called from here. A round's replies are corked and reach the socket in one write or writev when it ends.

  • At most one worker runs a connection at a time (the scheduled flag). Events the loop sees meanwhile only go into pendingEvents, and the round picks them up before it ends.
  • Output queued below WriteBufferHighWatermark no longer stops the read: the watermark bounds a connection's buffering, not its first queued byte. Stopping there left a pipelining client's requests in the kernel's receive queue and caused heavy retransmission.
  • A write edge only flushes flushable output. What the application holds with Cork waits for Flush, however writable the socket is.
  • A handler that panics has scheduled rolled back and its connection closed, and the panic goes on to the pool's panic handler.

TLS (fibtls.NewServer in front of any fib.Handler)

The handshake is a blocking crypto/tls call, so it runs on a pool of its own; the ciphertext it reads is still read from the socket by an engine worker and fed to it. Afterwards, AES-GCM and AES-CBC suites are protected by fib itself, decrypting on the worker straight from the round's read buffer.

  • readMu leaves one goroutine delivering plaintext at a time: while the handshake's worker delivers the first of it, an engine worker's feed waits.
  • During the handshake a worker only appends ciphertext and returns, so a round is never held up by it. A handshake worker is held by a slow peer for HandshakeTimeout at most.
  • OnClose never runs beside OnHandshake: a close before the handshake settles is kept as closeHeld and reported by the handshake's worker. Plaintext a peer sent right behind its handshake and then closed is still delivered first (dropsInput drops nothing while settling).
  • Sends are encrypted one at a time under wmu whichever goroutine makes them, so HTTP/2's stream workers queue here when they answer on one connection.

A worker reads and frames the connection, and hands each request's handler to the stream pool, going straight back to the socket. Responses are encoded on the stream workers and written directly, as far as the flow-control windows allow.
